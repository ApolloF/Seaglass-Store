# Seaglass

A Windows game launcher that finds installed games on its own (stores, external copies, game folders), launches them and tracks playtime, with a desktop mode and a controller-first big picture mode.

## Stack
- Backend: Go 1.27 on Wails v3 (pinned `v3.0.0-beta.26`; upgrade on purpose, never floating). No cgo; Windows APIs through `golang.org/x/sys/windows`.
- Frontend: Svelte 5 (runes) + TypeScript + Vite 8, Vitest. No UI library, no router.
- Styling: CSS custom properties in `frontend/src/app.css` (dark in `:root`, light under `[data-theme="light"]`); Barlow / Barlow Condensed.
- Data: JSON files with atomic tmp+rename writes (`%APPDATA%\Seaglass` for library/settings/keys/log, `%LOCALAPPDATA%\Seaglass` for art, game database, updates). No database.
- Shared parsing: `github.com/ApolloF/gamekit`.

## Commands
- Install frontend deps: `cd frontend && npm ci`
- Dev (app): `wails3 dev -port 9245` (or `task dev`)
- Dev (interface only, made-up games): `cd frontend && npm run dev:mock`
- Build: `wails3 build` → `bin/Seaglass.exe`
- Installer: `wails3 task installer VERSION=vX.Y.Z MAKENSIS=".../makensis.exe"`
- Regenerate bindings after changing exported service methods or their types: `wails3 generate bindings -f '-tags production' -clean=true -ts -i`
- Typecheck: `cd frontend && npm run check`
- Tests: `go test ./...` (CI also runs `-race`), `cd frontend && npm run test`
- Live tests (touch the real PC, gated by env vars): e.g. `WL_REAL_SCAN=1 go test -run RealScan -v ./internal/scan`
- End-to-end: `tools/harness/*.mjs` drive a dev build through `\\.\pipe\seaglass-dev` (see `tools/harness/README.md`).

## Check command
`go test ./internal/... && npm --prefix frontend run check && npm --prefix frontend test`
Run `npm --prefix frontend ci` once first. About 1 minute. It skips the root package (`go test ./...` needs `frontend/dist` from a build, because `main.go` embeds it) and the `-race` run; CI (`.github/workflows/build.yml`, job `windows`) does the full build, `go test ./...`, the race detector and the installer smoke tests. Keep it fast and keep it passing.

## Layout
- `main.go` — single instance, Wails app, service registration, tray.
- `internal/app` — services the interface calls (`services.go`, `launch.go`, …), `Core` (background loops, `emit` events), windows and tray, dev flags (`dev.go`).
- `internal/{scan,identify,library,settings,meta,launch,pad,syncer,owned,achievements,update,…}` — one concern each; see the README's Develop section.
- `frontend/src/lib` — `api.ts` (the only gateway to the backend; `api.real.ts` / `api.mock.ts`), `store.svelte.ts` (library state), `types.ts` (mirrors Go types), pure helpers with `*.test.ts` beside them.
- `frontend/src/desktop`, `frontend/src/bigpicture`, `frontend/src/overlay` — the three interfaces; shared pieces in `frontend/src/components` (check there first).
- `frontend/bindings` — generated by `wails3 generate bindings`; never edit by hand, but commit the output.
- `internal/torrent` (engine interface, `qbit/` qBittorrent sidecar), `internal/store/{jobs,feed,catalog,sources}`, `internal/safety`, `internal/installer`, `internal/app/store*.go` — the experimental store (`docs/experimental-store.md`; feed format in `docs/store-feed.md`). End to end: `node tools/harness/store.mjs`.
- `internal/store/discovery` (source index, crawl, grouping, queries), `internal/store/enrich` (Steam chart and reviews, Metacritic, HowLongToBeat), `internal/store/wishlist`; `internal/app/store_discovery*.go`, `store_enrich.go`, `store_wishlist.go`; the desktop Store in `frontend/src/desktop/Store.svelte` and `frontend/src/desktop/store/`. In the real app: `node tools/harness/discovery.mjs`.
- `docs/PLAN.md` — the plan and decisions per version.

## Conventions
- Settings: add fields to `internal/settings.Settings` with a default in `Defaults()` and validation in `normalize`; decide on purpose whether a field is `Portable` (follows the person to other PCs) or stays per PC. Mirror the field in `frontend/src/lib/types.ts` and `api.mock.ts`.
- New backend features expose methods on a service in `internal/app`, events through `Core.emit`; the interface calls them only through `api.ts`, with a mock implementation so `npm run dev:mock` keeps working.
- User-facing text is plain, short sentences; settings use `Toggle` rows with a title and detail.
- Comments explain why, in plain sentences; tests are named for the behaviour they check.
- Experimental features sit behind a per-PC setting (e.g. `experimentalStore`) under *Settings → Experimental*; with it off, nothing of the feature runs or shows.

## Definition of done
`go test ./...`, `npm run check` and `npm run test` pass; bindings regenerated if services changed; UI checked in mock mode, both themes, and at narrow widths.

## Git workflow
- Remote: GitHub `ApolloF/Seaglass-Store` (public). A fork-style edition of Seaglass: `sync.yml` brings Seaglass's `main` in every day.
- Branch, then PR, then CI (`build`, job `windows`), then merge only when the user says "ship it" (merge commit: the daily sync relies on Seaglass's history staying an ancestor of `main`).
- The daily sync opens a `sync/<date>` PR, starts `build` on it with `workflow_dispatch` (PRs made with `GITHUB_TOKEN` don't trigger `pull_request` runs) and tries to enable auto-merge. `build.yml` therefore keeps a `workflow_dispatch:` trigger.
- Releases: `docs/RELEASING.md` and `docs/store-edition.md`; only the maintainer tags.

## Secrets
- No `.env` is needed to build or run. The only tracked env file is `frontend/.env.mock` (no secrets; `.gitignore` allows it on purpose).
- Signing and release material (`SIGN_PFX_BASE64`, `SIGN_PFX_PASSWORD`, `SIGNPATH_API_TOKEN`, `SEAGLASS_RELEASE_KEY`, `SEAGLASS_FEED_TOKEN`) lives only in GitHub Actions secrets.
- Never commit real values. gitleaks runs on every commit; `.gitleaksignore` lists two known false positives (GOG Galaxy's public client secret).
